 # Cybersecurity SQL Lab: Dataset Documentation

## 1. Dataset Metadata & Overview

* **Source Repository:** Cybersecurity SQL Lab
* **Licence:** MIT License (open source; permits educational, academic, and non-commercial research use).
* **Format:** Raw CSV files (`data/raw/auth_logs_raw.csv` and `data/raw/employees_raw.csv`).
* **Size:** 527 raw authentication log records (`auth_logs_raw.csv`) and 20 corporate employee profile records (`employees_raw.csv`).
* **Date Collected:** 2026-11-17
* **What One Record Represents:**
  * `auth_logs_raw.csv`: a single user authentication attempt (login event), capturing username, login date, login time, origin country, source IP address, and success status.
  * `employees_raw.csv`: an individual employee profile, detailing assigned device ID, corporate username, department, and office location.

## 2. Privacy & Data Anonymisation Assessment

* **Real Personal Data:** None.
* **Anonymisation Status:** The dataset relies on synthetic corporate usernames (`jsmith`, `ajonson`, `mjohnson`), simulated hardware device identifiers (`D001` to `D020`), and private IP address ranges (`192.168.1.x`, `10.0.0.x`). No actual human personal identity data (such as real identity numbers, phone numbers, personal home addresses, or real email addresses) exists in the raw input files.

## 3. Data Quality Assessment (Reported Defect Counts)

* **Split Date & Time Fields:** 527 records store dates (`login_date`) and times (`login_time`) in separate text columns, requiring consolidation into a single Oracle `TIMESTAMP`.
* **Duplicate Rows:** 12 exact duplicate authentication log rows identified in the raw data streams.
* **Inconsistent Categorical Office Formatting:** 4 formatting variations of office locations (e.g., `'East-170'`, `'east 170'`, `'E170'`, `'East_170'`).
* **Inconsistent Boolean Data Types:** 527 success status values stored as mixed text representations (`'TRUE'`, `'FALSE'`, `'1'`, `'0'`), requiring conversion to standard numeric flags (1 or 0).

## 4. Entity Identification (5 Target Tables)

1. **`DEPARTMENTS`**: Stores organisational departments and physical office codes.
2. **`EMPLOYEES`**: Stores employee profiles, assigned device IDs, and account status.
3. **`AUTH_LOGS`**: Stores granular authentication event streams.
4. **`SECURITY_ALERTS`**: Stores threat detection alerts generated by high-risk login attempts.
5. **`QUARANTINED_ACCOUNTS`**: Stores the history of automated account locks executed by PL/SQL triggers.

## 5. Step-by-Step Normalisation (UNF → 1NF → 2NF → 3NF)

### 5.1 Unnormalised Form (UNF)

A flat, single structure combining employee details, office locations, authentication logs, and threat alerts.

### 5.2 First Normal Form (1NF)

* **Action:** Split the composite `Office_Dept` into distinct fields (`Office`, `Department`), combine `Login_Date` and `Login_Time` into an atomic `Login_Timestamp`, and assign primary keys.
* **Dependency Removed:** Removed composite attributes and repeating groups so that every column contains atomic values.

### 5.3 Second Normal Form (2NF)

* **Action:** Separate employee profile attributes (`Device_ID`, `Department`, `Office`) into an `EMPLOYEES` table so that non-key attributes depend entirely on `Employee_ID`.
* **Dependency Removed:** Removed partial dependencies by separating static employee profile details from individual authentication event logs.

### 5.4 Third Normal Form (3NF)

* **Action:** Remove transitive dependencies ($\text{Employee} \rightarrow \text{Department} \rightarrow \text{Office}$) by creating a dedicated `DEPARTMENTS` table.
* **Dependency Removed:** Removed transitive dependencies by moving office location codes and department names into a separate `DEPARTMENTS` entity.
